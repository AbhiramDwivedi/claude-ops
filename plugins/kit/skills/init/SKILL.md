# kit init

You are setting this project up so that agents working in it follow its real conventions and can't report done with broken lint or tests. Everything you propose must come from this repo's code, not from general best practice. A conventions section that could be pasted into any project is worthless; leave it out.

The kit plugin already ships four agent types with their model pinned: `kit:builder` (Sonnet, implements a brief), `kit:reviewer` (Opus, read-only review against the checklist), `kit:test-writer` (Sonnet, tests from the spec first), `kit:scout` (Haiku, read-only search). Don't recreate them per project. They are the generic fallback: the project's own persona agents (step 2, item 5) do the work in the areas they cover.

## 1. Scan

Use `kit:scout` agents or your own searches; read excerpts, not whole trees. Find:

- **Languages and frameworks**, from manifests (`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `*.csproj`, `Gemfile`, ...) and file counts.
- **Stack-areas and industry evidence**, from the helper: run `<python> <script> --repo <project root>`, where the script is `scripts/kit_scan.py` in this plugin (resolve it and pick the interpreter as in section 3). It prints JSON: each stack-area (`stack`, `framework`, the `area` directory, its `manifest` and `cite`, the files a persona for that area can point at) and `evidence`: the README titles and first paragraphs, the entity and table names read from declarations, and the most frequent domain nouns in identifiers, each with its file. It names no industry; that is your job. Read the files it names before you rely on them, and add any area it missed (a Dockerfile-only service, a SQL migrations directory, infrastructure code).
- **Industry and domain**: what industry the project serves and what its users do in it. Read the helper's evidence, then the README, `docs/`, the names of modules, classes and tables, and the data models (entities, schemas, types). Name the industry and the domain in one sentence each, for example "healthcare, outpatient appointment scheduling", and keep the list of files you read. Name one only when the evidence says so plainly. A dev tool, a library or a template has no industry: say so. When the evidence points at two industries or none, read more; if it is still unclear, ask the person. Ask the person only when the repo can't tell: one question, naming what you saw. Never guess an industry to fill the field.
- **Commands**: package scripts, `Makefile`/`justfile`/`Taskfile` targets, CI workflow steps. Name the exact lint, typecheck, format, test and build commands, and whether each can run on one file. CI is the best evidence of which commands the project really trusts.
- **Services and ports**: `docker-compose*`, `Procfile`, dev scripts that start several processes, hard-coded or env-driven ports.
- **Conventions in use**, each backed by two or more files you can cite: error handling (exceptions vs result types, where errors are logged or wrapped), module and directory layout, naming, how config and secrets are loaded, how tests are organised and what they mock, patterns that recur (repositories, handlers, hooks, DI). Note where the code is inconsistent; say so rather than picking a winner silently.
- **What exists already**: `CLAUDE.md`, `.claude/settings.json`, `.claude/agents|skills|commands`, `.claude/kit/`. You extend these; never discard what is there. If `.claude/kit/` exists, kit has run here before: say so and suggest `/kit:revise` instead, unless the person wants a fresh pass. If it exists without `.claude/kit/manifest.json`, offer that as its own small proposal: the manifest facts read from the current files (the gates' commands, the agents in use, the setup scripts), written with `write` as in section 3.
- **Checks already in place**: hooks in `.claude/settings.json` or `.claude/hooks/` that already lint, typecheck or test; a gate script; pre-commit tooling (husky, lefthook, pre-commit); CI. A check the project already runs on edit or on stop must not run twice. Propose kit's gates only for what is missing, and say which existing check covers the rest.
- **What a fresh worktree needs before tests pass**: dependency install (pnpm, npm, yarn, uv, poetry, pip), gitignored files the code reads (`.env*`, local config), generated code (Prisma, OpenAPI, protobuf, `.next`), Docker Compose services, a local database, lint/typecheck caches.
- **Tools that scan the whole repo** (`eslint .`, `prettier .`, test runners, file watchers, `tsc` with broad `include`): check that each one's ignore config excludes `.claude/worktrees/`, where agent worktrees live. Otherwise a check run in the main checkout also scans every agent's worktree. Check git too (`git check-ignore -q .claude/worktrees/x`): unignored, the worktrees leave the main checkout permanently dirty, so the stop gate runs the tests on every stop.

## 2. Propose

Show the person one proposal, grouped by file, with the full text of new files and a diff for changed ones. Open it with a line that states the industry and domain you found and the files it read, so the person can correct it before anything is written. Include only what the scan supports:

1. **`CLAUDE.md` conventions section.** Short: commands (exact), layout, and the conventions you found, each with a file reference. Under 60 lines; every line loads into every session.
2. **Quality-gate hooks** in `.claude/settings.json` plus small gate scripts in `.claude/kit/`. A lint or typecheck after each edit (PostToolUse on `Edit|Write|MultiEdit`), and the tests before the main agent stops (Stop), and before subagents stop (SubagentStop) when the tests take under about a minute. Use the templates in `hooks-reference.md` in this skill's directory, filled with the commands you found. Merge into existing settings; don't replace other hooks.
3. **If there is no linter or typechecker**, say so first and recommend the standard one for the stack (with its config). It catches more than any agent will, on every edit, for free. Offer to add it; don't add it without a yes.
4. **`.claude/kit/review-checklist.md`**, seeded from the conventions: 5 to 15 checkable items, each specific to this repo ("handlers return `Result`, never throw: see `src/api/users.ts`"), not generic ("code is readable"). Leave out anything the linter already enforces.
5. **Personas, on day 0.** Generic builders produce generic work, so the quality bar lives in project agent types specialised by stack and area. From the scan, list each stack and area (a manifest plus the directories it owns, and the framework it uses) and propose one editing persona for each stack-area pair, written to `.claude/agents/<name>.md` following the `kit:persona` skill in this plugin (read its `SKILL.md` first). The rule is one persona per stack-area: every area the code has gets a persona, so no area an agent may edit is left to `kit:builder`. A JVM backend, a TypeScript frontend, a Python service and a migrations directory in one repo are four personas, not one. Always add the read-only `product-owner` judge, written for the industry and domain you stated (section 1 of the proposal, and the `kit:persona` skill's product-owner rules); propose an architect reviewer judge only if the person wants one. Draft each persona to a scratch file outside the repo, then run the checker on the drafts: `<python> <checker> --repo <project root> <draft> <draft> ...`, where the checker is `scripts/kit_persona_check.py` in this plugin. It prints `OK:` or one `ERROR: <file>: <reason>` per problem (a Standard that cites no existing path, duplicates another persona's Standard or names nothing specific to its stack, which a stack outside the checker's table skips; a product-owner missing one of its six parts). Fix every error and run it again before you show anything. Then show each persona's full text. Its Standards are specific to its stack and area and cite repo files (the file where the pattern lives); a Standard that would fit any project is generic, so cut it. Where the repo has no habit yet, the ecosystem's idiom is allowed, marked as such. If you leave an area without a persona, say which and why in the proposal; the fallback is then named, not silent. Every path a persona names must exist now, and it holds no counts, versions or commands a script or doc owns. On a greenfield repo with no code, ask the person for the stack and areas, and propose from their answer. `kit:builder` and `kit:test-writer` remain the fallback for areas no persona covers.
5a. **Other project skills or commands, only where the repo clearly needs one**: a recurring multi-step procedure (release, migration, codegen). Each with the evidence; `/kit:revise` adds more later from real use.
6. **`.claude/worktree-setup.sh` and/or `.ps1`, only if a fresh worktree can't run the tests without setup, or the repo runs services that need separate ports.** The `worktrees` plugin runs it in each new worktree with `WORKTREE_PATH`, `WORKTREE_SLOT` and `PORT_BASE` set; slot N owns ports `PORT_BASE` to `PORT_BASE+9`. Use the stub in `hooks-reference.md` and keep only the steps the scan found. The rules behind it: install dependencies per worktree from the shared cache (pnpm store, uv cache), never copy or symlink `node_modules` or a venv (tools resolve the link back to the main checkout; an editable install in a shared venv imports the main checkout's code); copy gitignored config; regenerate generated code rather than copying it; give each slot its own Compose project and database; copy lint/typecheck caches only with a content-based cache strategy. Setup should finish in about 30 seconds, since every editing agent waits for it.
7. **Ignore entries** for `.claude/worktrees/` in `.gitignore` and in any repo-scanning tool's config that lacks one.
8. **The manifest's facts**, as one item: the JSON object `write` will record in `.claude/kit/manifest.json`, with exactly `checks` (`{name, kind, command, gate}`, gate `edit`, `stop` or `none`), `agents` (`{name, readOnly, declaredBy}`), `riskyPaths` (`{path, why}`) and `setupScripts`. List kit's own agents as `kit:reviewer` and `kit:scout` read-only and `kit:builder` and `kit:test-writer` not, declared by `kit`; a project agent, persona or judge, has its bare name and `declaredBy: "project"`. Editing personas are `readOnly: false`; the `product-owner` judge is `readOnly: true` as it has no write tools. Propose `readOnly: true` for a project agent only when its `tools` line lists none of `Write`, `Edit`, `NotebookEdit` and `*` (Bash is fine; no `tools` line means every tool, so not read-only), and never for a Claude Code built-in type such as `general-purpose`. Beside each read-only entry, say what it does: the stop gate skips that agent type, and its Agent calls skip worktree isolation, so it runs in the main checkout. The schema is `docs/manifest.schema.json` in this plugin.

End with the list of files you will create or change, and ask whether to write all of it, some of it, or none.

## 3. Write

Write only what the person approved. Then:

- Write the manifest from the approved facts, never before approval: pipe them to `<python> <script> write --repo <project root> --facts -`. The script is `scripts/kit_manifest.py` in this plugin: from this skill's base directory, `../../scripts/kit_manifest.py`, resolved to an absolute path. Use the first of `python3`, `python`, `py -3` that prints Python 3.9 or newer for `--version`. It prints one JSON line; show the person its `gates` statuses. A `kit_manifest: warning:` line on stderr means everything was written but the temp files it names were left behind; show it. `no-markers` means a gate predates the `kit:read-only-agents` markers: propose the current template for it. The lines between the markers belong to the script and are replaced on every run. On a non-zero exit every file is as it was, except any the line names as `<path> now holds the new bytes` (see exit 1); show its one stderr line, then:
  - exit 2: the facts are wrong; fix them and run again.
  - exit 3 `MANIFEST_CORRUPT`: the existing manifest is broken. Ask the person whether to rewrite it from the current files; on yes, rename it to `manifest.json.bak` and run `write` again. `write` keeps other plugins' agents only from a readable manifest, so first read the `.bak` as best you can (strip a UTF-8 BOM, try to parse it) and add every agent whose `declaredBy` is neither `kit` nor `project` to the new facts, unchanged; show those agents to the person as part of what they approve. If the `.bak` won't parse at all, tell the person that foundry and any other plugin that declared agents must declare them again (for foundry, re-run `/foundry:init`).
  - exit 3 `NEWER_VERSION`: a newer kit wrote it. Stop and tell the person to update kit.
  - exit 1 `IO_ERROR`: the OS refused the file the line names. Ask the person; don't retry around it. If the line says `<path> now holds the new bytes`, the script couldn't put that file back: tell the person, and when it adds `old bytes kept in <temp file>`, that the temp file holds the previous contents.
- Run each gate script once by hand (pipe it a sample hook input, as in `hooks-reference.md`) and show that it passes on the current tree, or fails for a real reason.
- Make the scripts executable on Unix (`chmod +x`).
- Tell the person what will now happen on edits and on stop, and that `/kit:revise` will suggest changes once there are a few weeks of sessions.

Whenever the setup changes later (a check, an agent, a risky path or a setup script added or dropped), run `write` again with the full new facts. Agents other plugins declared are kept.

Don't commit unless asked.

## Declare flow

When started with args `declare read-only: <type>, <type>` (foundry init does this), don't scan. Show the person the declaration, for example "foundry asks kit to mark `foundry:judge`, `foundry:cynic` read-only: no worktree, no stop-gate run". Each type must be a full `plugin:name`, all with one prefix; refuse anything else. On approval run `<python> <script> declare --repo <project root> --by <the types' prefix> --read-only <type>,<type>` and show its output. If it exits 3 with `NO_MANIFEST`, run the full init above and put the declared types in its facts' `agents` as `readOnly: true`, declared by their prefix. Any other non-zero exit: handle it as for `write` above, except that exit 2 means the declaration is wrong, so show it and stop. On exit 3 `MANIFEST_CORRUPT`, ask the person whether to rebuild the manifest, which takes the scan this flow skipped; on yes, rename it to `manifest.json.bak` and run the full init above, as for `NO_MANIFEST`. Its facts' `agents` get the `.bak`'s agents declared by neither `kit` nor `project`, as `write`'s recovery says, and the declared types as `readOnly: true`, declared by their prefix; a declared type replaces a `.bak` agent of the same name.
